# Medical Informatics — Teaching and Learning Design
 
**Programme:** Diploma in Biomedical Science, Ngee Ann Polytechnic
**Module:** Medical Informatics (Year 3, 10 weeks)
**Version:** 0.1.3 (13 November 2026; filename retained for stable reference)
**Status:** Working draft (v0.1.1: §13 decisions 1–3 confirmed, 1 Nov 2026; v0.1.2: PAIR adopted, concept grouping for W6/W8/W9 approved, G3/G4 accepted, blueprint reference updated, 12 Nov 2026; v0.1.3: references, development stages, SCORM requirements and NEHR rule updated — see §15, 13 Nov 2026)

**Planning assumptions** (marked ⚑) are design estimates, not NP requirements. Validate them against NP policy and pilot data.

## 1. Design principles in operation
 
| Principle | Operational rule |
|---|---|
| Problem before technology | Each week opens with a case event or guiding question, not a definition. |
| System before component | New systems are placed on the journey map before their functions are taught. |
| Laboratory as entry point | Every week's core example involves a laboratory result or specimen. |
| OAL prepares, practical applies | Practicals never re-lecture OAL content. |
| One primary artefact | Each practical produces one required output (syllabus D6). |
| Spiral with a lens | Recurring concepts state the new angle taken (syllabus D7). |
| Privacy from Week 1 | One privacy decision in each practical, Weeks 1–6 (D12). |
| Reasoning over recall | Formative and summative tasks reward justified judgement. |
| Fictional data only | All datasets and cases are synthetic. |

## 2. Weekly learning cycle
 
**OAL → practical → feedback → next OAL.** Each week's quiz data informs the practical entry check; each practical debrief feeds the next week's retrieval items.
 
### 2.1 OAL structure (120 min)
 
Target 4–6 learning objects per week; segments may be combined.
 
| Segment | Purpose | Format | Time ⚑ |
|---|---|---|---|
| 1. Case update and guiding question | Activate; state the week's problem | Short text or narrated slide; case-state line | 5 min |
| 2. Retrieval from earlier weeks | Spaced practice | 2–3 auto-marked items from prior weeks | 5 min |
| 3. Core explanation | Build concepts | 2–3 narrated segments, each ≤ 8 min, with workflow diagrams | 35 min |
| 4. Worked example | Model expert reasoning | Step-by-step example using lab data | 15 min |
| 5. Interactive activity | Apply with feedback | Drag-and-drop, classification or annotated case | 20 min |
| 6. Curated reading | Authoritative depth, Singapore context | One short source with a guiding question | 15 min |
| 7. Formative quiz | Check WLOs; surface misconceptions | 6–10 items with item-level feedback | 15 min |
| 8. Practical preparation | Ready students for the practical | Brief, role, materials, success criteria | 10 min |
| | | **Total** | **120 min** |
 
**Rules**
- Time estimates include pausing, note-taking and re-viewing ⚑; narrated time is roughly half to two-thirds of segment time.
- Introduce no more than five new key concepts per week ⚑. Weeks 6, 8 and 9 group their syllabus topics into five key concepts (approved 12 Nov 2026; no topics removed; see `05_Weekly_Learning_Architecture_W2-W10_v0.1.md`). Week 1 checked: five key concepts, at the limit, with the Singapore map as context only (W01 Stage A §3, §12).
- Any optional extension is labelled optional and excluded from the 120 min.
### 2.2 Practical structure (120 min)
 
| Segment | Purpose | Time ⚑ |
|---|---|---|
| 1. Entry check | Address misconceptions from OAL quiz data | 10 min |
| 2. Briefing | Scenario, student role, success criteria | 10 min |
| 3. Guided task | Worked-to-faded first part of the artefact | 35 min |
| 4. Checkpoint | Lecturer or peer feedback against criteria | 10 min |
| 5. Independent task | Complete the artefact, including the privacy decision | 35 min |
| 6. Debrief | Model reasoning, common errors, privacy and GenAI discussion | 15 min |
| 7. Exit ticket | One-question check on the week's key judgement | 5 min |
| | **Total** | **120 min** |
 
**Rules**
- The primary artefact is finished within the practical; no homework beyond OAL.
- **Confirmed:** face-to-face classroom delivery; class size ≤ 25; groups of 3–4 for tasks; individual exit tickets.
- Students take professional roles where useful (e.g. medical technologist, clinician, IT analyst, data-protection officer) to show differing information needs.
- Spreadsheet tasks (W3, W6) assume student computer access in the classroom; confirm with tool approval (§13, item 5).
- Week 10 follows the C3 structure in the blueprint, not this template.

### 3.2 Workload rules

2. No graded weekly tasks; summative work is limited to C1–C3.
3. C1 runs in a separate supervised slot where possible (blueprint §7).

## 5. OAL–practical alignment rules
 
1. Every practical task is preceded by an OAL worked example of the same reasoning type.
2. The OAL quiz tests the concepts the practical depends on; low-scoring items become the practical entry check.
3. OAL segment 8 states the practical success criteria in the same words as the artefact rubric.
4. The practical debrief names one link to the next week's topic.
5. No concept is first introduced in a practical, except deliberately in the W10 transfer case.

## 6. Formative assessment and feedback
 
### 6.1 Feedback opportunities per week
 
| Opportunity | Type | Feedback source |
|---|---|---|
| OAL interactive activity | Immediate | Automated |
| OAL formative quiz | Immediate, item-level | Automated, with explanation and remediation link |
| Practical entry check | Same day | Lecturer, whole class |
| Practical checkpoint | During task | Lecturer or peer, against success criteria |
| Debrief | End of practical | Model reasoning and common errors |
| Exit ticket | Next session | Lecturer summary to class |
 
### 6.2 Formative item standard
 
Each item specifies: correct answer; explanation; rationale for each distractor; feedback for correct and incorrect responses; WLO and cognitive level; likely misconception; follow-up or remediation.
 
### 6.3 Quiz settings (confirmed 1 Nov 2026)
 
- Ungraded; at least two attempts; feedback shown after each attempt.
- At least one item per WLO; about one-third at Apply or above.
- Retrieval items from earlier weeks included from Week 2.
### 6.4 Feed-forward to summative tasks
 
| Formative work | Prepares for |
|---|---|
| W3 audit, W4 table, W5 worksheet | C1 |
| W6 chart and critique (OAL check covers all three output types, G3), W7 matrix | C2 |
| W8 worksheet, W9 plan (with communication criterion, G4) | C3 |

## 7. Assessment principles
 
1. **Constructive alignment:** every summative criterion maps to an MLO component (blueprint §3–4).
2. **Assess each MLO once, at its highest level,** with individual evidence.
3. **Separate criteria for compound MLOs** (MLO3, MLO4, MLO5).
4. **Reasoning over polish:** criteria reward justification, verification and professional judgement, not length or fluency.
5. **Authenticity:** tasks use realistic laboratory and healthcare scenarios.
6. **Transfer:** summative scenarios are new; they do not repeat weekly practicals.
7. **Integrity by design:** scenario variants, supervised C1, individual C3 element.
8. **Transparent GenAI rules:** stated per component, with verification evidence (blueprint §5).
9. **Fictional data only.**
10. **Accessibility:** formats and conditions allow reasonable adjustments.
11. **Timely feedback:** feedback on C1 returned before C2; on C2 before C3 where the calendar allows (**TBC**).
12. **Moderation and grading:** follow NP requirements (**to be supplied**).

## 8. GenAI in teaching
 
- Follows syllabus §6.4: Rule (W1), Augment (W3, W6), Boundary (W5), Object (W7), Governance (W8), Advance (W9–W10).
- Independent attempt always precedes AI use.
- **PAIR (adopted 12 Nov 2026):** wherever students use AI, they document **P**roblem formulation → **A**I tool selection → **I**nteraction → **R**eflection. PAIR structures the Augment and Advance stages; it does not add AI use to weeks where §6.4 has none.
- Students submit a verification record whenever AI is used: claim → check → outcome. This forms the Reflection step of PAIR.
- Only approved tools; fictional data only; identifiable information is never entered.
- Lecturers model a verification in OAL before students are asked to do one (W3).
- AI outputs used as teaching objects (W5, W6) are generated by the lecturer in advance, archived with tool and date, and checked before release.

## 9. Inclusion and accessibility
 
- Captions and transcripts for all narration; alt text for diagrams; colour-blind-safe charts; keyboard-navigable interactions.
- Plain-language explanations with a module glossary (syllabus §11).
- Datasets readable without specialist software; spreadsheet tool **TBC** (syllabus §8, item 11).
- OAL is self-paced within the week.
- Delivery: SCORM 1.2 packages for NP Brightspace with bookmarking, completion status and score tracking, accessible navigation, visible audio controls where narrated, and local assets (project instructions §5; `Development_Standards.md` §10).
- Accessibility standard: WCAG 2.1 AA proposed (`Development_Standards.md` §9); final standard follows the Production Specification (**to be supplied**).
---
 
## 10. Privacy and data handling in teaching
 
- All patients, results and incidents are synthetic and non-identifiable.
- Datasets are checked for accidental realism (e.g. real NRIC formats) before release.
- No real patient information is requested from students, including from placements.
- GenAI confidentiality rule introduced in W1 and enforced throughout.
- Students never access NEHR or any real patient record for coursework, including on placement (W01 storyboard W1-LO5-S3, approved gate B; NEHR not permitted for teaching [Singapore Context R1]).
- Synthetic identifiers follow the case-state register (e.g. `RGH-` + 6 digits) and never resemble NRIC/FIN formats.
